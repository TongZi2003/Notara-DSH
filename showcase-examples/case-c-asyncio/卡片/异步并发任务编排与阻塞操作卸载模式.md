# 异步并发任务编排与阻塞操作卸载模式

## 内容

在实际工程中并发执行一批 I/O 任务（如批量请求 5 个接口或混合调用遗留同步库）时，无需手动逐个写 `task1 = create_task(...)`、`task2 = create_task(...)`，标准库提供了三套核心编排与卸载模式：

```python
import asyncio
import time

# 模式 A：使用 asyncio.gather 并发聚合一批可等待对象并按序收集返回值（Python 3.7+）
async def fetch_data(api_id: int) -> str:
    await asyncio.sleep(1.0)
    return f"data-{api_id}"

async def run_with_gather():
    # 自动将传入的协程包装为 Task 并发运行，返回结果列表顺序与传入顺序严格一致
    results = await asyncio.gather(*(fetch_data(i) for i in range(1, 6)))
    print(results)  # ['data-1', 'data-2', 'data-3', 'data-4', 'data-5']（总耗时约 1.0s）

# 模式 B：使用 asyncio.TaskGroup 结构化并发（Python 3.11+ 官方推荐）
async def run_with_taskgroup():
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(fetch_data(i)) for i in range(1, 6)]
    # 退出 async with 块时，保证所有任务均已完成
    results = [t.result() for t in tasks]

# 模式 C：使用 asyncio.to_thread 卸载无法改写的同步阻塞 I/O 函数（Python 3.9+）
def legacy_sync_request(api_id: int) -> str:
    time.sleep(1.0)  # 模拟 requests.get() 或同步文件/数据库读写
    return f"sync-data-{api_id}"

async def run_with_to_thread():
    results = await asyncio.gather(
        *(asyncio.to_thread(legacy_sync_request, i) for i in range(1, 6))
    )
    print(results)  # 总耗时约 1.0s，事件循环主线程未被阻塞
```

## 参考理解

### 1. 触发场景与核心动机

当你已经理解 [[卡片/直接await协程对象与create_task并发调度的区别|直接 await 协程对象与 create_task 并发调度的区别]] 后，在真实项目里往往面临两类高频工程诉求：

1. **批量异步任务编排**：需要根据一个动态列表（例如 5 个或 50 个 URL）并发启动一组任务，等待它们全部完成后按原顺序拿到结果列表，并妥善处理其中某个任务中途报错的情形。
2. **遗留同步阻塞代码兼容**：项目里某段底层逻辑依赖仅提供同步接口的第三方库（如传统的 `requests.get()`、同步 `boto3` 或本地大文件读写），直接放进 `async def` 会卡死事件循环，但短期内又无法重写整个底层库。

### 2. 方案选型权衡边界（Trade-off Analysis）

#### （1）并发编排选型：`asyncio.gather` vs `asyncio.TaskGroup`

在日常同步代码中，一个函数抛异常会直接中断 `for` 循环；但在异步并发中，当 5 个任务同时在后台跑，第 2 个任务在 0.3 秒时抛出异常，其余 4 个还在跑的任务该怎么处理？这正是 `gather` 与 `TaskGroup` 的核心分水岭：

| 对比维度 | `asyncio.gather(*aws, return_exceptions=False)` | `asyncio.TaskGroup()`（Python 3.11+ 结构化并发） |
| :--- | :--- | :--- |
| **返回值获取** | 直接返回与入参顺序一致的结果列表 `results = await asyncio.gather(...)`，写法极简。 | 在 `async with` 块内收集 `task` 对象，退出块后通过 `[t.result() for t in tasks]` 获取。 |
| **单个任务抛异常时的默认行为（核心差异）** | 当 `return_exceptions=False`（默认）时，第一个异常会立即向上抛给调用方，但**其余 4 个未完成的任务不会被自动取消**，仍会作为“孤儿任务”继续在后台消耗网络和数据库连接。 | **强安全保证**：只要组内任一任务抛出异常，立即自动向组内其余未完成任务发送 `cancel()` 取消信号，并等待它们全部完成清理后，统一打包为 `ExceptionGroup` 抛出，绝不泄漏后台孤儿任务。 |
| **容错收集需求** | 设 `return_exceptions=True` 时，报错任务的异常对象会直接作为列表元素返回，适合“允许部分接口失败、成功多少算多少”的聚合场景。 | 默认采用“一损俱损”的事务式语义；若需单任务容错，需在子协程内部捕获异常并返回兜底值。 |

#### （2）阻塞处理选型：原生异步库替换 vs `asyncio.to_thread` 线程卸载

当遇到同步阻塞调用（参见 [[卡片/案例-async函数内误用同步time.sleep与requests导致假并发的诊断与修复|案例：async 函数内误用同步 time.sleep 与 requests 导致假并发的诊断与修复]]）时，有两种改造路径：

1. **路径一：替换为原生异步 I/O 库（首选）**
   - **做法**：将 `time.sleep()` 替换为 `await asyncio.sleep()`，将 `requests.get()` 替换为 `httpx.AsyncClient` 或 `aiohttp.ClientSession`。
   - **优势**：全程在单线程事件循环内通过操作系统多路复用（epoll/kqueue）完成，无多线程切换开销，可轻松支撑上千个并发连接。
2. **路径二：使用 `await asyncio.to_thread(func, *args)` 卸载到工作线程池（次选兜底）**
   - **运作机制**：`asyncio.to_thread` 会在后台默认线程池（`ThreadPoolExecutor`）中借用一个独立操作系统线程去执行同步函数 `func(*args)`，同时返回一个可等待对象让当前协程在主线程上非阻塞挂起（[[卡片/事件循环EventLoop与await主动让出控制权机制|事件循环 EventLoop 与 await 主动让出控制权机制]]）。等到后台线程执行完毕，事件循环再唤醒当前协程取回返回值。
   - **适用边界与失效条件（GIL 限制）**：
     - **适用**：**I/O 密集型（IO-bound）** 同步函数（如 `requests.get`、同步数据库查询、磁盘文件读写），因为等待 I/O 期间底层 C 代码会释放 Python 全局解释器锁（GIL），但受限于线程池默认最大线程数（通常为 `min(32, os.cpu_count() + 4)`），不宜用于成百上千的高并发请求。
     - **不适用（失效边界）**：**纯 Python 的 CPU 密集型（CPU-bound）** 计算（如在纯 Python 中做百万次哈希或大循环计算）。由于纯 Python 字节码执行时始终争抢同一个 GIL，使用 `to_thread` 无法利用多核 CPU 加速，此时应改用 `loop.run_in_executor(ProcessPoolExecutor(), ...)` 多进程池。

### 3. 工程实操必查防坑清单

1. **检查 `gather` 的入参展开**：`asyncio.gather` 接收的是多个位置参数 `*aws`（如 `asyncio.gather(coro1(), coro2())` 或用星号解包生成器 `asyncio.gather(*(coro(i) for i in range(5)))`），切勿直接把列表 `[coro(i) ...]` 不加 `*` 传进去。
2. **检查 `to_thread` 的传参形式**：必须把函数名与参数分开传入 `asyncio.to_thread(sync_func, arg1, arg2)`，**严禁写成 `asyncio.to_thread(sync_func(arg1, arg2))`**——后者会在调用 `to_thread` 之前就直接在主线程同步执行 `sync_func(arg1, arg2)`，导致主线程照样被阻塞！
3. **检查高并发限流**：当并发任务数达到数百个以上时，直接 `gather` 全部任务可能瞬间打满目标服务器或耗尽本地端口，应配合 `asyncio.Semaphore(limit)` 控制最大同时活跃请求数。

### 下次探讨

2. **异常边界推演**：假设用 `asyncio.gather(task1, task2, task3)` 并发写入三条远程记录，当 `task1` 在第 0.1 秒因网络超时抛出异常时，默认情况下 `task2` 和 `task3` 会停下来吗？如果业务要求“一旦有一个失败，立即中止其余请求”，应如何改写？
