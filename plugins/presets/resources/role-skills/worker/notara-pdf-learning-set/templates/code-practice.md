## 参考理解
<!-- 填写说明（模板列出写卡时要注意的要素，按内容自然组织，不要求每张卡机械补齐同一排子标题）：
【1. 本类核心关注点（识别信号、突破口形成与失效边界）】
- 异常表象与突破口形成：写清具体现象（如“写了 async/gather 但 5 个 1 秒任务仍耗时 5 秒”或“某个子任务报错后其余任务仍在后台跑”）如何一步步缩小排查范围、定位到真正阻塞事件循环或泄漏引用的那一行；
- 根因定位（Root Cause）与最小可运行实现（MVP）：顺着执行栈说明为什么原写法失效，给出修复后的最小可运行代码及实测输出对比；
- 方法选择理由与失效边界（Trade-off）：说明为什么选该方案（如 `asyncio.gather` vs `asyncio.TaskGroup`、原生异步客户端 vs `asyncio.to_thread` 线程池卸载），以及在异常取消、Python 版本或纯 CPU 密集负载（受 GIL 限制，`to_thread` 仍无法实现多核并行）下何时失效。

【2. 高频漏检与防坑要素（代码审查与排错必查）】
- 必查隐式同步阻塞（Blocking Call in Coroutine）：检查 `async def` 内部是否混入了 `time.sleep()`、`requests.get()`、同步文件/数据库驱动等直接卡死操作系统线程的调用；
- 必查错误传播与孤儿任务：检查并发任务中某一个任务抛出异常时，其余并发任务是否需要立即联动取消，防止后台残留孤儿任务耗尽连接池；
- 必查并发度失控与引用丢失：检查是否对成百上千个请求无限制并发（需配合 `asyncio.Semaphore` 限流），以及后台 `create_task` 是否保存在集合中。

【3. 白板与可视化推演建议（怎么摆白板）】
- 优先使用 普通辨析题（在对话中说明理由）引导学习者诊断错误代码为何阻塞或进行方案选型决策；
- 使用 `frames` 对比修复前（主线程被同步调用锁死）与修复后（任务挂起让出主线程或卸载到工作线程）的实测执行时间轴，或用 普通填空题 挖空修复代码的关键行。

【4. 知识结构与具体关系】
- 排错案例通过 tags 中的实体双链挂接实际用到的语言特性和方法。共性工程模式用 type: method，在自身“## 前序依赖”声明事件循环或调度等直接基础；具体代码执行顺序留在案例分析中。
- 比较工程模式或排错案例时，在“## 横向联系”说明负载、接口和错误传播的差异；普通回查链接不当作学生已建立的关系。

【5. 复习抽考关键步（Key Step）与变式方向（写在末尾 ### 下次探讨）】
- 抽考关键步：面对一段并发失效或存在异常泄漏隐患的异步代码，无提示指出阻塞主线程的具体行号并给出两种修复路径（替换为原生异步库 vs `to_thread` 卸载）及其适用条件；
- 变式探讨：在末尾 ### 下次探讨 留 1～2 个改变负载类型（如从 I/O 阻塞改为纯 Python 大循环 CPU 计算）或模拟其中一个任务中途抛异常时的演化问题。 -->
